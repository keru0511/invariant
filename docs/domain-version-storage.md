# ドメイン別の内容アドレス型版管理

## 方針

[Gitのオブジェクトモデル](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)の、
内容を識別子で参照し、変更されていない部品を共有する考え方を採用しています。
Gitのリポジトリ形式やコマンドを実装するものではなく、D1上の独自形式です。

- 履歴の単位は workspace + domain。各ドメインが独立した現行版を持つ
- versionIdは履歴の識別子。提案由来の版では従来のUUID由来IDを維持する
- contentHashはスナップショットの内容を表すSHA-256。履歴IDとは別にする
- 新しい版にはparent_version_idを記録する。承認時の元版検査は従来どおり原子的に行う
- 内容が同じなら、異なる履歴IDから同じオブジェクトを参照できる

## 保存する部品

`domain_objects`には正規化したJSONを保存します。オブジェクトキーはソートし、
配列の順序は意味・トレースを維持するため変えません。Unicode表記や式の意味を推測して統合しません。

- rule: ルール本体と条件式
- function: 入力・説明・policy情報とルールへの参照
- catalog: 関数への参照と検索用の小さな見出し
- type / example / unknown / conflict: 個別の定義・検証例・未解決事項
- model: catalogと各メタデータへの参照

modelの内容からversionIdを除き、履歴IDが違うだけで同じ内容が重複しないようにします。
同じカタログでも未解決事項等が違えば、modelのcontentHashは異なります。

オブジェクトはworkspace/domain内でだけ共有します。別ドメインや別workspaceのハッシュを
指定しても、その範囲外のデータを読み出すことはできません。

## 読み書きと整合性

新しい版のmodel_jsonと提案のmodel_json/authoring_jsonは、小さな参照JSONになります。
参照先のオブジェクトを復元し、ハッシュと構造を検証してから評価します。
欠損・ハッシュ不一致・種類の不一致はエラーとし、推測したモデルへ置き換えません。

新規オブジェクトと版/提案は同じD1 batchで保存し、途中失敗なら全体を取り消します。
[公式のbatch仕様](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)に合わせた構成です。
既存オブジェクトを上書きせず、同じハッシュの再保存は何もしません。

取得は複数ハッシュをまとめ、書き込みも複数行をまとめます。
[現在のD1制限](https://developers.cloudflare.com/d1/platform/limits/)を踏まえ、
読み取りは最大82、書き込みは最大96のバインド引数に抑えています。
検索はcatalogの見出しを利用し、各版の全ルールを復元しません。

MCPのdescribe/evaluateには、新形式の場合snapshot.contentHashとsnapshot.parentVersionIdを返します。
過去の版を明示すれば、現行版とは独立に再評価できます。

## 移行と制約

マイグレーション0004を適用してから対応アプリを使います。
旧形式のJSONをそのまま持つ版も読み取れます。既存の本文を削除・置換する移行は行いません。
旧版の不明な親子関係は推測しません。新規保存から親を記録します。

新形式を書き始めた後は、旧コードだけへ戻しても参照JSONを解釈できません。
アプリを戻す場合も対応readerを残す必要があります。本PRは本番マイグレーションやデプロイを実行していません。

複数の変更案は保持できますが、自動マージは行いません。元版が古くなった案は再作成・再確認が必要です。
版や提案の削除、保存期限、未参照オブジェクトの自動削除は実装していません。
新しい内容・履歴メタデータ・会話の引用が増えれば、保存量は引き続き増えます。

## 検証した保存量

合成カタログで1ルールの優先度を変えながら20版保存した場合、
旧方式のJSON本文合計113,920バイトに対し、共有オブジェクトと参照JSONの合計は44,129バイトでした。
この条件では約61.3%削減です。SQLiteの索引・ページや履歴メタデータを含む総ディスク量ではありません。
小さなモデルや最初の1版では、オブジェクトの管理情報により増える場合もあります。

同一内容の再保存でオブジェクト数が増えないこと、1ルール変更でrule/function/catalogの3部品だけが増えること、
旧版の復元、ドメイン分離、破損拒否、保存失敗時の取り消しを実SQLiteで検証しています。
ローカルWorker/D1/HTTPでも、同じ入力に対して旧版のallowと新版のdenyを再現します。
